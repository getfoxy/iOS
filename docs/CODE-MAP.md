# Code map

Where things are in the repository, how the names work, and which screen is
which. `ARCHITECTURE.md` says why it is shaped this way; `build/README.md` has
the build in full.

## What is in the repository

```
Web/                what ships into the app bundle
  index.html        the UI — GENERATED, do not edit; see build/
  foxy-wallet.js    the ecash wallet: keys, proofs, mint calls, storage — GENERATED from build/wallet/
  foxy-tor-gate.js  the screens shown while Tor connects, or cannot
  foxy-send-progress.js foxy-receive-progress.js foxy-move-progress.js   the animation overlays
  cashu-ts.js bip39.js qrcode.js   vendored libraries — see Web/VENDOR.md
build/              the source of index.html and foxy-wallet.js — see build/README.md
  app/              the app class in parts, every screen's behaviour; joined into foxy-app.js
  wallet/           the wallet in parts; joined into Web/foxy-wallet.js
  markup.html       every screen's markup

  shell/            the rest of the page: head.html, manifest.json, assets/, page.json

  Bridge/           the native bridge (FoxyBridge), the paste control, notifications
  Tor/              Tor (TorService), the transport fallback, the built-in bridges
```

`Web/index.html` is built by `tools/pack-index.py`. It joins `build/app/*.js`
into `build/foxy-app.js` and `build/wallet/*.js` into `Web/foxy-wallet.js`
(`tools/join-sources.py`), then packs the app class, `build/markup.html`,
`build/foxy-render.js` and `build/shell/` into the page. Edit a part in
`build/app/`, `build/wallet/` or `build/shell/`, or `build/markup.html`, pack,
install. `tools/unpack-index.py` still takes the app class and the markup out of
a page, but no longer writes a shell. Pack also recomputes the hash the page's
Content-Security-Policy uses to allow its one inline script, so a pack is
required after any change to the loader. Read `build/README.md`.

## Naming

Bindings and methods are prefixed by the screen they serve: `sp` split, `bk`
backup, `cf` confirm, `nm` new mint, `tx` history and detail, `cl` the wallet
list. Every binding the markup reads is computed in the render function of the
screen that shows it, in `build/app/22-` to `27-render-*.js`, and gathered by
`renderValsBase()` in `build/app/21-render-values.js` (`build/README.md` has the
layout).

## The screens

Every screen is a `<sc-if>` in `build/markup.html` keyed on a flag computed in
its render function, named in the table. The flag name and the screen name are often different, and
guessing between them has cost three separate rounds of wrong edits: `confirm`
is the *receive* screen, not the send confirmation; a Lightning send lands on
`paid`, not `sendDone`.

| screen | flag | computed in | what it is |
|---|---|---|---|
| `home` | `isHome` | `renderHome` | balance, price chart, RECEIVE and SEND |
| `amount` | `isAmount` | `renderAmount` | the keypad, both directions |
| `confirm` | `isConfirm` | `renderReceive` | **receive**: the invoice and its QR |
| `paid` | `isPaid` | `renderPaid` | the confirmation after money moves — "PAYMENT RECEIVED", or "WITHDRAWAL SENT" when `payOut` is set. **A Lightning send ends here.** |
| `sendHow` | `isSendHow` | `renderSend` | scan, paste, ecash, contacts, type |
| `sendType` | `isSendType` | `renderSend` | typing a lightning address |
| `sendScan` | `isSendScan` | `renderSend` | the camera |
| `sendDone` | `isSendDone` | `renderSent` | the screen *under* the sending overlay, and the confirmation for a spend found elsewhere or a balance check. Its settled branch is overtaken by `paid`. |
| `tokenOut` | `isTokenOut` | `renderToken` | a generated ecash token, with its QR |
| `history` | `isHistory` | `renderHistory` | the transaction list |
| `txDetail` | `isTxDetail` | `renderTxDetail` | one transaction: amounts, fee, mint, payment id, audit trail |
| `contacts` | `isContacts` | `renderContacts` | saved handles |
| `switchMint` | `isSwitchMint` | `renderMints` | the mint list |
| `newMint` | `isNewMint` | `renderNewMint` | adding a mint by address |
| `importSeed` | `isImportSeed` | `renderRestore` | the twelve-word restore grid |
| `rsConfirm` | `isRsConfirm` | `renderRestore` | what a restore found, before adopting it |
| `bkStart` `bkPhrase` `bkVerify` `bkDone` | `isBk…` | `renderBackup` | the backup flow |
| `depConfirm` `sendConfirm` `reqOffer` and the other `*Confirm` keys | `isConfirmShell` | `renderConfirmShell` | one confirmation shell, filled in by `confirmSpec()`; a scanned payment request (`reqOffer`) is filled in by `requestSpec()` |
| `sendFail` `netLost` and the other `BLOCKED` keys | `isBlocked` | `renderBlocked` | an action that did not happen, and why |
| `spAmount` … `spAllPaid` | `spIs…` | `splitVals` | splitting a bill |

The Tor screens are not in this table. `Web/foxy-tor-gate.js` builds its own
DOM, the same way `foxy-send-progress.js` does.

**Before editing a screen, confirm which one you are looking at.** The fastest
way is to search `build/app/` for a string you can see on the device:
"WITHDRAWAL SENT" leads to `paidTitle`, and therefore to `paid`.
